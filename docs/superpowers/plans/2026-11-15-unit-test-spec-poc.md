# 単体テスト仕様書生成PoC Implementation Plan

> **For agentic workers:** 実施指示後は superpowers:executing-plans または superpowers:subagent-driven-development で進める。本依頼では計画だけを作成し、実装・文書生成・環境変更は実施しない。

**Goal:** プログラム仕様書とC90ソース1件から、根拠・手順・期待値が追跡できる単体テスト仕様書のJSON正本をAIで作成し、固定テンプレートからOfficeCLIでWordへ展開する工程を検証する。

**Architecture:** 既存の正本・`.c`・`.h`をハッシュで固定する。仕様からの試験設計、コードからの追加観点、独立レビューを経てJSONを確定し、固定スクリプトが検証・納品文書展開・来歴記録を行う。既存C試験と結果ログは、期待値作成後に比較資料として対応付ける。

**Tech Stack:** IBM Bob IDE、Bob同梱OfficeCLI、Python 3.12標準ライブラリ、JSON、Git、DOCX。新規MCPサーバーは作らない。

**Spec:** `prototypes/routine-code-poc/input/spec.json`、`prototypes/routine-code-poc/include/AlarmQualification.h`、`prototypes/routine-code-poc/src/AlarmQualification.c`。文書生成の先行実装は `packages/routine-spec-officecli/skills/routine-spec-doc/`。

## 1. 今回の対象と方式

対象は `PS-RTN-ALM-001 / RTN-ALM-001 / AlarmQualification_Update`、仕様revision 0.1、`draft_trial` の1ルーチン。10回の有効ONサンプルによる成立、飽和、リセット、再成立、入力エラーを扱う。仕様正本の未承認仮定ASM-01〜03、未決Q-01〜04を引き継ぐ。

| 方式 | 利点・追加作業 | 今回の扱い |
|---|---|---|
| JSON正本 → Word | 既存OfficeCLIの行複製・差込み・内容照合・構造検査を再利用できる。単体テスト用スキーマとテンプレートは新設する | **推奨案**。小規模で第三工程を確立する |
| JSON正本 → Excel | ケースの絞込み・一覧比較に向く。XLSX用アダプター、セル照合、印刷確認の検証が追加になる | 同じ正本からの第二出力として次段階 |
| JSON正本 → WordとExcel | 両形式の整合性を同時検証できる | 最初のPoCでは出力経路が増えるため見送る |

Wordを一次出力とするのは計画上の推奨であり、利用者による納品様式の最終指定ではない。既存プログラム仕様書テンプレートへテスト項目を無理に詰め込まず、用途別に新設する。

## 3. Review Focus

1. 「10回目」と「10T経過」の混同を防ぐ。文書の時間解釈を検査し、経過時間を測定したと記載しない。
2. 無効入力時の任意signal_on、複合エラー優先順位、エラー時の全バイト保持を具体的ケースに含める。
3. 各ケースが他ケースの実行結果に依存しないよう、初期状態・旧出力を毎回指定する。
4. 仕様・ソース・ケースIDの参照切れ、コード改訂後の古い対応表、列挙件数の誤りを検出する。
5. 仕様書完成、文書表示確認、試験実施済み、要求承認済みを別々の状態として扱う。

## 4. 作成する正本とテンプレート

JSON正本は `unit-test-spec.json`、文書IDは `UTS-RTN-ALM-001`、初版0.1、状態は `draft_trial` とする。安定したID、一定のキー順、UTF-8・改行付きインデントを採用する。Wordの修正は正本へ戻して再展開する。

| 正本の項目 | 必須内容 |
|---|---|
| `document` / `target` | 文書ID・版・作成AI・未承認状態、対象関数、入力ファイルとハッシュ |
| `environment` / `assumptions` | C90、ホスト検証と実機検証の区分、定数の解釈、非重複領域・所有権の前提、ASM/Qの引継ぎ |
| `cases[]` | 安定ID、目的、仕様参照、初期state・旧out、ポインタ条件、各手順の入力と期待戻り値・state・out、無更新条件、判定基準 |
| `families[]` | 安定ID、値集合・列挙順・展開ID規則・件数、初期条件、手順、独立した期待値規則、仕様参照 |
| `static_checks[]` | 禁止API・ループ等・共有状態・検査順序のレビュー項目、確認方法、対象範囲 |
| `coverage[]` / `open_issues[]` | 仕様から試験への対応、未対象理由、仕様と実装の差異、未決事項 |

実際の結果・実施者・実行日時・証跡は別の `records/execution-record.json` で管理する。未実施時にも状態を明示する。人による承認欄は試験結果と分ける。

`INT_MIN`・`INT_MAX`・`UINT_MAX` はCの記号定数として表現し、32bitの数値へ決め打ちしない。ポインタ条件は「有効なオブジェクト／NULL」として表し、不正アドレス・領域重複・競合を注入するケースは作らない。期待値規則は説明と有限の値集合で明確にし、任意コードのevalや被試験関数で計算しない。

仕様参照は既存IDを使い、判定表等のIDがない要素は固定入力に対するJSON Pointerを併用する。ソース参照は関数名・ファイルハッシュを必須とし、行番号だけに依存しない。JSON Schemaによる形の検査と、重複・参照・件数等の意味検査を分ける。既存の簡易バリデーターは対応キーワードが限定されるため、そのまま完全なJSON Schema実装として扱わない。

Wordテンプレートは、文書情報、対象・環境・前提、ケース一覧、詳細手順、パラメータ族、静的確認、対応表、未決事項で構成する。詳細は「ケースID・手順／初期条件と入力／期待結果／根拠」の4列を基本とし、時系列はステップごとの行へ展開する。A4、表見出しの繰返し、ページ番号を設定し、全ページの可読性を確認する。大量系列を全行出力しない。

## 5. 初期ケース設計案

代表16ケースと列挙4族を起点とする。最終IDと手順は独立レビュー時に確定し、必要な不足ケースは根拠付きで追加する。件数を満たすことだけを合格基準にしない。

| ケースID | 独立した初期条件から確認する内容 |
|---|---|
| UT-ALM-001 | 初期0から有効OFF：戻り値0、count=0、qualified=0、event=0 |
| UT-ALM-002 | 初期0からON9回：各回count=1〜9、qualified/event=0 |
| UT-ALM-003 | 初期9からON1回：count=10、qualified=1、event=1 |
| UT-ALM-004 | 初期10からON100回：毎回count=10、qualified=1、event=0 |
| UT-ALM-005 | 初期0からON9回→OFF→ON：最後count=1、途中OFFは0 |
| UT-ALM-006 | 初期0からON9回→無効→ON：最後count=1、途中無効は0 |
| UT-ALM-007 | 初期10からOFF→ON10回：リセット後、10回目だけ再成立 |
| UT-ALM-008 | 初期10から無効→ON10回：同上 |
| UT-ALM-009〜011 | stateのみNULL／outのみNULL／両方NULL：-1、有効な領域は不変 |
| UT-ALM-012 | NULLと不正入力・不正状態が重なる場合：-1が優先、有効な領域は不変 |
| UT-ALM-013 | 初期状態11、不正sample_valid=2：-2が状態異常より優先 |
| UT-ALM-014 | 初期状態UINT_MAX、有効sample・signal_on=2：-2が状態異常より優先 |
| UT-ALM-015 | 初期9、sample_valid=0・signal_on=2：入力を無視し正常リセット |
| UT-ALM-016 | 2個の独立状態を交互に更新し、成立・リセットの非干渉を確認 |

エラー試験はstateとoutを既知の全バイトで初期化して保存し、旧outにはevent=1も設定する。戻り値と、有効な各領域の全バイト不変を比較する。NULL時に他オブジェクトを読まないことは、動作結果だけで証明せず静的確認にも割り当てる。

| 族ID | 定義と規模 |
|---|---|
| FAM-ALM-001 | 旧count 0..10 × {ON、OFF、無効時signal_on=INT_MIN/-1/0/1/2/INT_MAX}：88組。ONの期待値は判定表に基づく明示値で定義 |
| FAM-ALM-002 | 不正対象{sample_valid、有効時signal_on} × 不正値{INT_MIN,-1,2,INT_MAX} × 旧count{0,9,UINT_MAX}：24組。いずれも-2、無更新 |
| FAM-ALM-003 | 旧count{11,UINT_MAX} × {有効ON、有効OFF、無効sample・signal_on=2}：6組。いずれも-3、無更新 |
| FAM-ALM-004 | 初期0、{有効ON、有効OFF、無効}の長さ11の全列：177,147系列。各サンプル後を照合するため1,948,617呼出し照合 |

族4の期待値は、入力履歴の末尾から最大10個の連続有効ONを数えて定義する。現在と直前の履歴から成立イベントを求める。被試験関数の状態更新分岐を複製しない。列挙順・先頭/末尾の具体例・展開IDと期待値をレビューする。

集計は「代表ケース数」「族数」「族内の組合せ/系列数」「呼出し照合数」を分ける。既存の1,948,941チェックと新規仕様書のケース数を一致させる目標は置かない。重複する境界ケースと列挙族は根拠が異なるものとして明示する。

- [ ] `new-job` は既存コードPoCのjobを読取り、正本・C/H・生成記録を照合して新規領域へコピーする。
- [ ] 作者へ提示する入力と、後で比較する既存試験・旧結果を分ける。作者の参照範囲と使用AIを記録する。
- [ ] Python、Bob IDE、OfficeCLIの実体・版・ハッシュを環境票へ記録する。既存配布で承認したOfficeCLIは1.0.144。異なる場合は互換性確認を行い、新配布版で固定する。自動取得や黙った生成器切替は行わない。

### B：仕様から試験を設計する

- [ ] 作者は仕様から代表ケース・族・静的確認項目を記述する。
- [ ] コードからガード条件・書込み箇所・未使用の外部API等を確認し、仕様との不一致または追加試験観点を記録する。
- [ ] JSONの型・必須項目・重複ID・仕様参照・族件数・対象ハッシュを検査する。対象外事項に理由と後続確認先を付ける。
- [ ] 期待値設計をハッシュ付きで固定し、独立レビュアーが各ケースの再実施可能性と期待値根拠を確認する。レビューで直す場合は新しい版として残す。

### C：固定資産を作る

- [ ] `skills/routine-unit-test-spec/SKILL.md`、`references/authoring.md`、`assets/schema/unit-test-spec.schema.json`、`assets/templates/unit-test-spec-v01.docx`、固定スクリプトを新設する。

- [ ] 文書生成では改行・日本語・`{{...}}`を含む文字列、長文、表の複数ページを確認する。残存差込みタグは、入力に意図的に含めた文字列と区別して検査する。
