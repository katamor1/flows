# 具体的な機能要求から3工程への展開例

この資料は、利用者が示した2つの自然文要求を使い、先の導入計画を具体化したものである。ルーチン名・構造・未決事項は分析案であり、承認済みのプログラム仕様ではない。RTOSの実際の提供関数名は未提示のため創作しない。

自然文の機能要求はそのまま入力にできる。初段のエージェントが、原文を保存したうえで、要求項目、既存仕様への参照、設計候補、未決事項に分解する。利用者が最初からJSONで要求を書く必要はない。

## 1. 全工程で共通参照するプロジェクト情報

| 共通情報 | この2例で必要になる内容 |
|---|---|
| RTOS・DLL契約 | 周期コールバック、画面側からの呼出し文脈、提供API、CPUロック、ABI、時間・資源上限 |
| 信号辞書 | U.XXXX／G.YYYYの物理・論理対応、極性、有効性、更新周期、入力スナップショット、出力所有者 |
| パラメータ辞書 | MMM／MM1／MM2の型、単位、範囲、既定値、取得API、変更可能な運転状態、反映時点 |
| ログ規約 | 追記バッファの契約、ファイルZZZZの対応、時刻、書式、文字コード、満杯・書込み失敗時の方針 |
| UI公開規約 | 公開関数の形、メッセージ取得・列挙方式、バッファ長、文字コード、所有権、同時呼出し |
| 既存実装 | 再利用できるアラーム管理・追記バッファ、現在の2段移動平均、初期化・停止処理と既存テスト |

先にこの情報を版付きカタログへ整備し、各要求では差分と参照を指定する。個別要求に書かれていない項目は、承認済み共通仕様から継承できる。共通仕様にも根拠がない項目を質問・設計判断として提示する。

## 2. 例A：10周期連続ONによるアラーム・画面公開・ログ予約

### 2.1 原文から確定できる内容

- 監視対象はPLC信号U.XXXX。
- 発報条件は10 RTOS周期連続のON。
- 成立時に表示灯信号G.YYYYへON指令を出す。
- 画面がアラームメッセージ文字列を取得できる公開APIを用意する。
- 点灯時刻・信号名・メッセージを、ファイルZZZZへの追記用バッファに積み込む。

要求は「追記バッファへの積込み」までを含む。周期処理からファイルへ直接追記する実装に置き換えない。既存基盤がバッファ消費・ファイル追記を担当するなら、その仕組みを再利用する。投入成功とファイルへの永続化完了は別の状態として扱う。

### 2.2 仕様確定前に確認する内容

| 論点 | 確認が必要な理由 |
|---|---|
| 10周期の意味 | 「各周期の入力取得で10回連続ON」と「経過時間10T以上」のどちらかを確定する。欠落・遅延周期の扱いも異なる |
| 入力の有効性 | 通信断、古いPLC入力、更新停止をON継続・OFF・異常のどれとして扱うか |
| 発報後の解除・再発報 | 入力OFFで解除するか、ラッチしてリセットを待つか。再発報・再記録の条件は何か |
| ログ頻度 | 発報時に1回か、ON継続中にも記録するか。重複防止が必要か |
| 点灯時刻 | 条件成立、ON指令、出力反映、実点灯検出のどの時刻か。フィードバックなしに実点灯時刻を保証しない |
| 信号名 | ログにU.XXXX、G.YYYY、両方、表示用の論理名のどれを記録するか |
| 同時アラーム | 他の要求もG.YYYYを使用する場合の合成・優先順位・消灯権限 |
| バッファ満杯 | 破棄・再試行・欠落通知の方針、再試行時の重複防止、表示灯動作との関係 |
| 画面公開 | アクティブなメッセージだけか履歴も含むか。停止・解除と同時に読まれた場合の一貫性 |
| 文字列・時刻 | 文字コード、最大長、終端、時刻API、時計補正・同一時刻のイベントの区別 |

周期ごとのサンプル確認を採用し、最初のONサンプルを1回目とする場合、10回目は最初のONサンプルから9T後になる。実際の信号変化からの遅延には、サンプリング位相、PLC通信、出力反映時間も関係する。「10周期」を無条件にタイマの`10×T`待ちへ変換しない。

### 2.3 ルーチン仕様への分割候補

候補は責務を説明するための名前であり、実際の公開API名や関数数を決めるものではない。既存ルーチンに同等機能があれば再利用する。

| ルーチンの責務 | 入力と状態 | 出力・副作用／制約 |
|---|---|---|
| 初期化・終了 | 設定、信号・ログ先の対応、内部状態 | 必須設定の検証、状態初期化、終了中呼出しへの対応 |
| 連続ONの判定 | 周期ごとの信号値・有効性、確認カウント、発報状態 | 成立／未成立／新規発報の判定。I/Oやログ操作から分離できる |
| 発報の反映 | 新規イベント、既存アラーム管理の契約 | G.YYYYへの指令、公開状態更新、ログ予約。各操作の失敗方針を明示 |
| 画面向け取得 | 呼出し元バッファまたは既存公開規約 | メッセージと状態の整合したスナップショット。所有権・長さ・排他を規定 |
| ログ予約 | イベントの時刻・信号名・メッセージ・ログ先 | 既存の追記バッファAPIへ投入。上限時間、満杯・再試行を規定 |

判定と副作用の分離により、10周期の境界はホスト単体試験、API呼出しはモック試験、出力反映・共有状態・時間は実DLLの結合試験で確認できる。

発報イベントには、必要に応じてイベントID、時刻、信号識別、メッセージの不変な内容をまとめ、画面とログが同じイベントを参照できる設計を提案する。バッファ内に一時文字列へのポインタだけを置かず、コピーまたは寿命が保証された参照を用いる。物理出力とキュー投入を単一の原子的操作として実現できるとは仮定せず、部分失敗を仕様に含める。

### 2.5 単体テスト仕様への展開候補

次の具体的期待値は、**「10回目の有効ONサンプルで発報、発報時に1回記録」**を承認した場合の候補である。解除・再発報等の未決事項には勝手に期待値を設定しない。

| ケース | 入力・条件 | 確認内容 |
|---|---|---|
| A-01 | ONを9回 | 発報せず、点灯イベント・ログ予約はない |
| A-02 | 続けて10回目のON | この周期で新規発報。ON指令と公開情報とログ予約が契約どおり対応する |
| A-03 | ON9回→OFF1回→ON9回 | 途中OFFで連続性が切れ、まだ発報しない |
| A-04 | ONを長時間継続 | 同じ発報を毎周期記録しない。カウントはオーバーフローせず動作する |
| A-05 | 発報後にOFF／リセット／再度ON | 承認した解除・再発報条件と記録件数に従う |
| A-06 | 入力無効、PLC更新停止 | 承認した入力有効性の契約に従い、更新停止時の扱いを検証する |
| A-07 | ログバッファ満杯・投入失敗 | 点灯・公開状態・再試行・欠落通知を合意した方針で扱い、周期を無制限に待たせない |
| A-08 | 画面取得と発報・解除が同時 | 文字列切れ、破損、寿命切れ、状態とメッセージの不整合がない |
| A-09 | 同一表示灯を複数イベントが使用 | 既存の出力合成・所有権を守り、別アラームの表示を誤って消さない |
| A-10 | 既存ログ消費処理との結合 | 予約した時刻・信号名・文字列が、規定の形式でZZZZへ追記される。永続化失敗の扱いを確認 |

CPUロックの対応・最大保持時間、使用APIの引数・順序・回数、API失敗時の後始末は各ケースへ追加する。バッファ消費処理が既存基盤の責務なら、A-10は結合試験とし、DLL単体試験と区別する。

## 3. 例B：2段目をガウス関数型フィルタへ切り替える

### 3.1 要求から分かる処理構造

```text
位置移動指令
    → 既存の第1段移動平均（パラメータMM1）
    → MMMがOFF：既存の第2段移動平均（パラメータMM2）
       MMMがON ：仕様を確定したガウス関数型フィルタ
    → 既存の後段処理
```

これは要求から整理した候補構造である。実際の入力・出力時点、MM1／MM2の意味、丸め位置は既存コード・仕様で確認する。既存の第1段やOFF時の挙動を変える必要があるなら、元の要求へ設計変更を戻す。

### 3.2 「ガウス関数型」だけでは計算仕様が一意にならない

ガウス重みのFIR、既存の制御ライブラリの機能、近似フィルタ等のどれを指すかを確認する。FIRを選ぶ場合でも、窓長、標準偏差、係数、正規化、履歴、初期化、遅延が必要になる。

参考としてSciPyのGaussian windowは点数と標準偏差を別のパラメータに持ち、最大値を1に正規化する。平滑化のDCゲインを1にしたい場合の「係数和を1にする」正規化とは区別する。また配列向けGaussian filterには境界拡張の選択がある。これらの既定値を、そのままオンライン制御の仕様にしない。[SciPy Gaussian window](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.windows.gaussian.html)、[Gaussian filterの境界処理](https://docs.scipy.org/doc/scipy/reference/generated/scipy.ndimage.gaussian_filter1d.html)

### 3.3 決定すべき数値・状態・時間の契約

| 論点 | 仕様に必要な内容 |
|---|---|
| フィルタの定義 | 数式または承認係数・既存実装の版。対象は位置・差分・速度等のどの量か |
| MM1・MM2の意味 | サンプル数、時間等の既存定義。MM2を窓長・標準偏差へどう対応させるか、追加パラメータが必要か |
| 因果性と遅延 | 利用できる過去履歴、先読みの有無、出力時刻、許容遅延。オンライン処理で未取得の将来入力を暗黙に使わない |
| 数値表現 | 位置の単位・範囲、float／double／固定小数点、演算順序、丸め・飽和、誤差上限 |
| 起動・履歴不足 | ゼロ埋め、初期指令値で埋める等の規則。起動・停止・再開時の状態 |
| MMM切替 | 動作中の変更可否、反映周期、状態の移行・再初期化、出力の不連続の許容範囲 |
| MM1・MM2等の変更 | 設定値を一貫した組で取得する方法、再計算、状態移行、無効値・破損値の扱い |
| 計算資源 | 最大窓長、履歴バッファ、スタック、1周期の演算上限、係数生成の実行文脈 |
| 制御性能 | 許容追従遅れ、速度・加速度・ジャーク等の要求、後段や停止動作への影響 |

既存のパラメータ辞書にこれらが定義されていれば、その版を参照する。未定ならAIが一般的な既定値を選んで確定扱いしない。

### 3.4 ルーチン仕様への分割候補

| ルーチンの責務 | 契約・制約 |
|---|---|
| 設定の検証・確定 | 基盤APIで取得したMMM／MM1／MM2等を検証し、反映周期を決める |
| 係数・作業領域の準備 | 承認したモデルから係数を準備。実行文脈と最大時間を規定し、周期内の重い計算を避けられるか判断する |
| 第2段フィルタの周期更新 | 固定上限の履歴・演算量で1サンプルを処理。提供APIや不要な動的確保を混入させない |
| モード・設定の切替 | 停止中のみ変更、状態移行、並行計算と補間等を比較し、必要な方式を承認する |
| 初期化・リセット | 初期値、停止・再開、無効設定からの復帰時の履歴を定義する |

FIRを採用する場合の例は、承認した有限係数列`a[i]`を用いて`y[k] = Σ a[i] × x1[k-i]`を計算する形である。`x1`は第1段出力とする候補。係数和・窓長・各係数・数値表現・遅延を契約に含める。これは採用済みアルゴリズムではない。

切替時の補間や新旧フィルタの並行実行は、計算量と応答を変える。滑らかそうに見える方式を自動採用せず、既存の設定変更規約と時間予算で判断する。係数計算を準備段階へ移す案も、許可された初期化・設定変更の実行文脈があることを確認する。

### 3.5 単体テスト仕様・評価方法への展開候補

| ケース | 入力・条件 | 独立した確認基準 |
|---|---|---|
| B-01 | MMMがOFF、既存の代表入力系列 | 既存2段移動平均の出力と一致する。ビット一致／許容誤差を先に定める |
| B-02 | MMMがON、定常入力 | 承認した初期化・過渡応答後のゲインと定常誤差を満たす |
| B-03 | インパルス入力 | 承認係数・モデルの応答と照合し、履歴の方向・添字・段間接続の誤りを検出する |
| B-04 | ステップ・ランプ・実運転の指令系列 | 出力値、遅延、過渡応答、追従誤差を許容値で確認する |
| B-05 | 最小／最大パラメータ、無効値 | バッファ上限、係数正規化、除算、エラー方針を確認する |
| B-06 | 正負の最大位置・微小な変化 | オーバーフロー、丸め・飽和、累積誤差を確認する |
| B-07 | 起動・履歴不足・リセット・再開 | 承認した初期化と過渡挙動に一致する |
| B-08 | MMMや窓長等を変更 | 承認した反映時点、履歴の扱い、不連続・遅延の上限を満たす |
| B-09 | 最大窓長・切替・他DLL負荷 | 実ターゲットで演算・ロック・APIを含む時間予算を満たす |
| B-10 | 既存の運動制御との結合 | 平滑化後の指令と装置応答が要求した制御性能・停止条件を満たす |

期待値は、生成したCコードの出力をコピーして作らず、承認済み数式・係数と独立した参照モデルから作る。係数和や定常応答等の性質も併用する。Python等の参照モデルは開発・評価用に置けるが、C90 DLLの実行依存にはしない。参照モデルとCの数値差を許す場合は、その許容誤差と根拠を先に定める。

## 4. 導入計画への反映

| PoCの順序 | 目的 | 最初の合格条件 |
|---|---|---|
| A. アラーム要求 | 原文→状態仕様→APIを使うDLL→テスト仕様→Word／Excelまでを一貫して確認 | 9／10周期境界、途中OFF、発報・ログ頻度、API制約、公開情報とログの整合が確認できる |
| B. フィルタ要求 | 既存処理の変更、数値モデル、状態・遅延・資源制約を確認 | OFF時の既存互換、ON時の承認モデル一致、切替仕様、誤差・時間予算が確認できる |

アラーム側は既存アラーム管理・バッファ機構を確認し、必要なら設定データの追加で実現する。フィルタ側は既存実装と承認モデルの有無を確認する。両方を毎回ゼロからコード生成する前提にしない。

導入基盤には、共通の「状態を持つ周期処理」「副作用を伴う発報イベント」「API契約」「数値フィルタ」「モード切替」の仕様項目と検査を用意する。型に当てはまらない要求は汎用生成へ黙って流さず、追加設計が必要なものとして扱う。

既存計画の8週間・60〜84人日は、資料・SDK・既存実装・試験環境を利用できる限定PoCの概算として維持する。ただし、ガウスフィルタそのものの制御設計・装置調整・新規HIL構築が必要なら別工数とする。今回の例だけで工数削減率や自動化率は確定できない。
