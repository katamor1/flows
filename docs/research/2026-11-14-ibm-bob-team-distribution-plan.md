# IBM Bobと同梱OfficeCLIを前提とするチーム配布計画

更新: 利用者の「生成まで統一」の指示を受け、OfficeCLIでWord生成・構造検査を行う0.2.0を実装した。現行の配布手順と検証結果は[OfficeCLI生成の実装と検証](2026-11-14-officecli-generation-validation.md)を適用する。以下は段階移行前の配布案として残す。

作成日: 2026-11-14。対象は既存Win10 RTOS実行基盤へ追加するC90 DLLの開発支援。Bobと文書ツールは開発側で使用し、制御DLLへ組み込まない。

## 1. 今回の決定

**初回は、プロジェクトのGitリポジトリにBob用スキル・ルール・固定資材を収容して配布する。** 既検証の生成器でJSON正本からWordを展開し、Bob同梱OfficeCLIの標準ツールで読取り・OOXML構造検査を行う。OfficeCLI自体はチーム用キットへ再同梱しない。

OfficeCLIによる生成への統一は、繰返し表の変換アダプターと同梱版の機能確認が済んだ後の改訂とする。これにより、チーム配布を始めるために検証済の変換処理を書き直す必要がない。

前回案のCodex向け検索先やプラグイン構成は配布先として採用せず、今回のBob用配置に置き換える。最初の受入対象は引き続き10周期連続ON判定の試作仕様1ルーチンであり、任意の要求からの仕様書作成やC実装の自動化までを今回の配布物で保証しない。

## 2. 調査で確認したBob側の仕組み

| 確認したこと | チーム配布への適用 |
|---|---|
| プロジェクトの `.bob/skills/` に `SKILL.md` と補助資材を置ける | スキルと固定スクリプト・テンプレートをまとめてGit管理する |
| グローバルスキルと同名の場合はプロジェクトスキルが優先される | 案件の利用版を優先する。ただし重複名は導入時に確認する |
| `.bob/rules/` をプロジェクト共通ルールとして共有できる | 仕様書作成時に使うスキル、正本、資材改訂の境界だけを短く記述する |
| 標準Officeツールに `office_read` と `office_edit` がある | 初回は `office_read` で生成物の内容と構造を検査する |

スキル配置・対応資材は[IBM Skills](https://bob.ibm.com/docs/ide/features/skills)、ルール配置は[IBM Custom rules](https://bob.ibm.com/docs/ide/configuration/rules)、Officeツールと `mode: "validate"` は[IBM変更履歴](https://bob.ibm.com/docs/ide/changelog)で確認した。

Bobの変更履歴には、プラグインへのスキル・モード・ルール・MCPの収容やグローバル `~/.bob/plugins/<plugin-name>/mcp.json` も記載されている。ただし、その記載だけから他製品の `plugin.json` を互換と判断しない。初回は配置が明示されたプロジェクトスキルを使い、Bobネイティブプラグインでの横断配布は、採用IDE版の形式・検出・更新を検証してから行う。[IBM変更履歴](https://bob.ibm.com/docs/ide/changelog)

## 3. 配布単位とファイルの所有者

```text
対象プロジェクト/
  .bob/
    rules/20-routine-spec.md           仕様書作業を正しいスキルへ誘導
    skills/routine-spec-doc/
      SKILL.md                         Bobへ渡す手順
      references/authoring.md           正本の記述と対応範囲
      scripts/specflow.py               通常操作の固定CLI
      scripts/_engine.py                検証・Word差込みの固定実装
      assets/schema/                   正本契約
      assets/templates/                固定Word書式
      assets/examples/                 記述例
      requirements.txt                 生成器の固定依存
      release.json                     固定資材の版・ハッシュ
  project-profile/                      RTOS API・DLL ABI・C90規約等の案件固有契約
  spec-jobs/<job-id>/
    package-lock.json                   この案件が使う生成器の版
    source/spec.json                    仕様内容の管理正本
    renders/<run-id>/                   入力控え・Word・manifest
```

`project-profile/` は次の実RTOSルーチンを扱う段階で整備する設計上の配置であり、今回のZIPに実API一覧を仮作成しない。ログ、CPUロック、基板レジスタI/Oは既存RTOS提供関数を通す制約、呼出し文脈、許可／禁止API、周期と時間予算、エラー時の扱いを案件契約として版管理する。

| 資材 | 作成・変更の担当 | 通常のBob作業 |
|---|---|---|
| スキル・ルール・生成器・スキーマ・テンプレート | キット保守担当 | 既配布版を参照・実行する |
| RTOS API・ABI・規約・時間予算 | 基盤／案件の設計担当 | 正式な契約を参照し、不明点を未決事項にする |
| 要求とルーチンJSON正本 | 担当者＋Bob、設計レビュー担当 | 正本を作成・改訂する |
| Word、入力控え、manifest | 固定生成器 | 新しい展開IDへ出力する |
| 内容・表示・構造の確認記録 | 担当者＋Bob | 未確認と確認済を分けて記録する |

最初の1プロジェクトでは、保守担当が配布候補を確認し、`.bob` の対象フォルダをプロジェクトのPRで追加する。各人が自分のグローバルスキルへ任意にコピーして更新する運用を避け、プロジェクトのチェックアウトによって同じ版を利用する。

複数プロジェクトへ展開するときは、キットの原本リポジトリからタグを固定した配布アーカイブを作り、プロジェクト側へ同じバイト列を取り込む。更新は保守担当のPRで行う。AIが案件開始のたびに生成器やテンプレートを作り直す工程は設けない。ボリュームが小さい初期段階は、この取り込み方式で十分である。

## 4. 同梱OfficeCLIの利用範囲

OfficeCLIが同梱されることは利用者からの環境前提として採用する。一方、BobのOfficeツールから使える操作と、上流OfficeCLIのCLI全機能は区別する。

| 操作 | 初回配布での扱い |
|---|---|
| JSON正本の検証、繰返し表展開、Word生成 | 既検証の固定生成器を再利用 |
| 生成Wordの読取り・構造確認 | Bob標準 `office_read` を使用する受入試験を行う |
| OOXMLスキーマ検査 | Bob標準 `office_read` のvalidateモードを使用する |
| 生成物の手修正 | 正本へ変更を戻して再展開する。文書編集を試す場合は確認用の複製を使う |
| OfficeCLIのmerge／batchによる生成 | 同梱版の呼出し契約とアダプターの検証後に追加 |
| 印刷時の改ページ、日本語フォント、罫線、文字あふれ | 実際の納品確認環境で表示を確認する |

初回キットの生成器はPython 3.12、python-docx 1.2.0、lxml 6.1.1を使用する。この開発支援環境はOfficeCLIと別に必要であり、同梱OfficeCLIがあるだけで全依存が揃うとは扱わない。各PCで環境を揃える負担が大きければ、保守側で生成器を固定環境ごと配布する実行形式へまとめる。制御DLL側のC90制約とは独立した選択である。

### 既存テンプレートの扱い

上流のmerge仕様は `{{document.id}}` のようなドット記法を説明する一方、配列の自動解決を行わず呼出し側で展開するよう定めている。[OfficeCLI merge仕様](https://github.com/iOfficeAI/OfficeCLI/wiki/command-merge)

既存Wordテンプレートの繰返し表は、`w:tblCaption="repeat:<配列パス>"` と見出し行＋原型行という、この試作固有の契約である。標準mergeだけでこの契約を処理できるとは判断しない。OfficeCLIへ移行するなら、配列と原型行の解決、行複製、値の整形・差込み、原型行削除、残留トークン・行数の検査を固定コードで実装する。

batchを使う場合も、Bobが毎回編集命令を考えるのではなく、正本と固定対応表から命令列を組み立てる。メッセージ文字列はデータとして渡し、シェル命令文字列へ結合しない。上流batchには版によるロールバック動作の違いがあるため、同梱版で失敗時の非公開・後始末を確かめる。[OfficeCLI batch仕様](https://github.com/iOfficeAI/OfficeCLI/wiki/command-batch)

Bobの公開資料からは、同梱バイナリの固定配置パス、PATH登録、外部スクリプトからの直接呼出し、Officeツール経由のmerge／batch利用までを確定できなかった。アダプター改訂では、採用環境の実体と公開インターフェースを先に確認する。上流の最新バージョンをBob同梱版と同一視せず、実行時に別版を自動取得しない。

## 5. 版固定・更新・証跡

生成器の `release.json` と案件の `package-lock.json` は今回の配布候補でも再利用する。これらが照合するのは生成器・資材・Python依存であり、現行CLIはBobや同梱OfficeCLIの版を自動検証しない。

Bob側の受入試験では次を記録し、チーム標準の環境票とする。今後自動照合を追加する場合は、この環境票を読む独自処理として実装し、Bob標準設定と混同しない。

| 記録項目 | 確認方法 |
|---|---|
| Bob IDEの実ビルドと有効な標準Officeツール | IDEの製品情報・ツール一覧・受入試験ログ |
| 同梱OfficeCLIの版・実体ハッシュ | 取得できる公開経路で確認。取得不可なら未確認と利用インターフェースを明記 |
| キット版・スキーマ版・テンプレート版 | releaseと各SHA-256 |
| 正本・入力控え・出力 | manifestと各SHA-256 |
| RTOS SDK/API契約・コンパイラ | 実システム接続を扱う段階で版を記録 |
| 表示確認環境・フォント | ページ確認の環境と結果 |

Bobの更新とキットの更新は別管理にする。Bobや同梱OfficeCLIが更新された場合は、既存正本を使う短い互換性検査を実施してからチーム標準を更新する。旧案件のロックを単に書き換えて通過させない。

OfficeCLIへのレンダラー切替では、最初に内容・行数・型・書式・フィールド保持を旧生成器と比較する。実行系が変わるとDOCX内部メタデータ等も変わり得るため、異なる生成器間のバイト一致だけを受入条件にしない。納品物の来歴には実際の出力ハッシュを残す。

## 6. プラグインとMCPを追加する条件

| 方式 | 採用する場面 | 今回の判断 |
|---|---|---|
| `.bob/skills`＋`.bob/rules` のGit配布 | 1～少数プロジェクトで、案件の版に合わせて使う | 初回の標準 |
| Bobネイティブプラグイン | 多数のリポジトリへ一括配布・有効化・更新したい | 採用Bob版で配布形式を実証してから追加 |
| ローカルMCP | IDと正本を渡すだけのツールへ実行を集約し、同じ生成器を複数クライアントから呼びたい | 今回は追加しない |

Bobはプロジェクト `.bob/mcp.json` とグローバル `~/.bob/settings/mcp.json`、ローカルSTDIOを扱える。MCP化するなら既存本体の外側に `describe_profile`、`validate_spec`、`render_spec` 等を加え、固定資材を再実装しない。Bobの標準Office操作を利用するためだけに、別のOffice MCPを設ける必要はない。[IBM MCP in Bob](https://bob.ibm.com/docs/ide/configuration/mcp/mcp-in-bob)

スキル・ルール・編集範囲指定は、エージェントへの手順やツール制限として利用する。固定資材の書換えを強制的に防ぐ必要がある場合は、パッケージの配置先を実行アカウントから書込み不可にする。MCPも通常はBobと同じ権限で動くため、追加だけで別の保護境界ができるとは扱わない。今回の配布候補はACLや既存Bob設定を変更しない。

## 7. 初回導入の作業と受入条件

| 順序 | 作業・担当 | 完了の証拠 |
|---|---|---|
| 1 | 保守担当が配布候補と採用Bob環境を確定 | 配布ハッシュ、IDEビルド、Python依存、標準Officeツール一覧 |
| 2 | 保守担当が対象プロジェクトへ限定したフォルダをPRで追加 | `.bob` 全体を置換せず、既存スキル・ルールとの衝突がない |
| 3 | 担当者が新しいBob会話でスキルを使用 | Skills設定でプロジェクトスキルの検出を確認し、固定CLIが使用される |
| 4 | 担当者が記述例から案件を作り、文書版だけ変更 | JSON差分、Wordへの反映、資材ハッシュ不変 |
| 5 | Bobの標準Officeツールで生成物を検査 | `office_read` の読取りとvalidate結果を保存 |
| 6 | レビュー担当が4ページの表示と内容を確認 | 文字欠け・表欠け・ページ番号・内容の確認記録 |
| 7 | 欠落資材・対応外閾値・同名出力を試す | 再生成による自己修復や上書きをせず停止する |
| 8 | チームの利用版としてリリース | 受入結果と、残る前提・未決事項を添付 |

スキルは会話内で一度読み込まれるため、版更新の受入は新しい会話で行う。Bobの標準Planモードは実行系と使える編集対象が異なるので、正本JSONの編集とCLI実行を含むこの試験にはAgentモードを使う。[IBM Skills](https://bob.ibm.com/docs/ide/features/skills)、[IBM Modes](https://bob.ibm.com/docs/ide/features/modes)

この受入が済んだ後に、実RTOS APIを使う別ルーチンを1本追加する。そこで汎用スキーマと案件プロファイルの不足を確かめ、その後にコード作成・単体テスト仕様書用のスキルを同じ配布体系へ加える。今回の10周期判定の形式をそのまま全制御ルーチンへ適用しない。

## 8. 今回用意する配布候補と未確認

配布候補は `packages/ibm-bob-routine-spec-pilot`。既存routine-spec-kit 0.1.0のスキル・固定コード・資材を変更せず、ZIP内でBobのプロジェクト配置へ収容する。Bob用の短いルール、導入説明、配布メタデータを追加する。OfficeCLI本体、Bob設定、自動承認設定、MCP設定、他製品のプラグインmanifestは含めない。

検証範囲は、ZIP配置、元資材との一致、展開先の `.bob/skills` 配下からの既存CLI実行、元のDOCXの再現である。Bob IDEによるスキルの実起動、同梱OfficeCLIの実検査、チームの表示環境での確認は受入試験として残す。これは本番導入済・Bob動作認証済の配布物ではない。
