## 呼出し側への契約

1. 初回の `state.on_count` を0にし、同じ判定対象の状態を周期間で保持します。状態・結果は有効で重ならない書込み領域とし、他の実行中呼出しの領域とも重ねず、他タスク・画面側との同時参照や変更を防ぎます。本関数内に排他処理はありません。
2. 提供RTOS APIを使って取得した同一周期の入力スナップショットを渡します。1周期に1回呼び、欠落検出後は次の判定前に `sample_valid=0` を通知します。信号取得や周期欠落の検出は本関数では行いません。
3. `sample_valid` は0/1、有効時の `signal_on` も0/1です。無効時の `signal_on` は検査せず、正常な状態を0へ戻します。不正状態（10超過）は無効入力時にも-3となり、暗黙に修復しません。
4. 戻り値0の場合だけ結果を消費します。-1（NULL）→-2（論理入力不正）→-3（状態不正）の順で検査し、エラーでは状態・出力を変更しません。残った旧結果を新規イベントとして再利用しないでください。
5. 有効ONの10回目で `qualified=1` と `became_qualified=1`。ON継続中は10で飽和し、新規イベントは繰り返しません。OFFまたは無効入力で判定状態を解除し、その後10回で再成立します。これは表示灯・アラーム表示の解除条件を定義しません。
6. 出力、画面公開、時刻取得、ログ予約、必要な排他は、呼出し側から提供RTOS API経由で接続します。APIの定義が未提示のため接続コードは生成していません。Win32やファイルへの直接操作を追加する必要はありません。

この判定はサンプル数の判定です。周期Tなら最初のONから成立までは9Tであり、周期間の物理的な連続ONや経過時間を保証しません。
