# プログラム仕様書からC90ルーチンを作る

入力の管理正本を根拠に、ルーチン本体と仕様対応表を作る。仕様書・生成コード・試験結果の来歴を残し、固定スクリプトや独立試験を案件ごとに再生成しない。

## 入力と実装判断

1. JSON正本、対象の関数/型/引数、入出力・状態・エラー優先順位、呼出し周期、実行時間・排他の制約を読む。Wordと正本が食い違ったら正本との差異を報告する。
2. [実装とレビューの指針](references/implementation.md)を使い、仕様に定義された範囲だけ実装する。仕様に欠落・矛盾があれば具体的な箇所を挙げ、完成済みとして扱わない。試作仕様を製品承認済みに変更しない。
3. 外部操作が必要なルーチンでは、既存RTOSの正式API契約と対象コンパイラ/ABIを先に確認する。未提示のレジスタ名、API、呼出し規約、DLLエクスポート、ロック方式を推測しない。確認できる独立した計算・判定部分は進め、接続に必要な未決事項を残す。
4. ソースを作り、仕様ID・処理手順とコードを対応付けた `traceability.md` を作る。正常経路だけでなく、状態更新・異常時の副作用・呼出し側への割当も説明する。

## 固定検証プロファイル

この配布版の自動検証は、既存PoCの `AlarmQualification_Update / PS-RTN-ALM-001 revision 0.1` の正本ハッシュに限定する。この入力なら [アラーム用の実行手順](references/alarm-profile.md)を読む。

- 固定 `scripts/codegen.py` で新規jobを準備する。完了済みの実装は同梱しない。AIが編集するのは `src/AlarmQualification.c` と `traceability.md`。
- `input/`、`include/`、`tests/`、`tools/`、ロック、配布資材を変更して検査に合わせない。仕様を変更する場合はプロファイル改訂として扱う。
- 実際の生成AI・版・Bob実行の有無を `record` で世代別に記録し、`verify` で既存の固定検証器を実行する。修正後は新しいgeneration/run IDを使い、過去の記録を上書きしない。
- エラーが資材・入力・環境の不一致なら原因を報告する。別ツールの自動取得、資材の再生成、検査の弱体化で自己修復しない。

それ以外のルーチンでも前節の実装判断は使える。自動検証ツールは未対応として、チームが指定した正式ビルド・試験手順を使う。アラーム用のヘッダや試験を別の仕様へ流用しない。適切な試験がなければ「未検証の実装案」として提示し、合格を主張しない。

## 完了時の報告

ソース/ヘッダ、対応表、入力の版・ハッシュ、生成AI、実行した検証コマンドと結果、残る未決事項を示す。ホストのC90コンパイル・試験合格と、正式コンパイラ・DLL ABI・RTOS結合・WCETの検証を分ける。単体テスト仕様書の納品文書作成は別工程で扱う。
